## Output-contract taxonomy

| Category | Guarantee | Required `exactness_notes` |
|---|---|---|
| `exact` | The result is the mathematically correct value | None required |
| `approximate` | The result differs from the correct value by at most the stated bound | The bound formula or precision |
| `heuristic` | The result may be incorrect; no bound is claimed | The failure mode (when it can be wrong) |
| `conditional` | Correct under a named unproven mathematical hypothesis | The hypothesis (e.g., "assumes GRH") |

Source: `docs/capability-records.md` §Fields. These categories are fixed for the product lifetime.
A capability record that uses any other `exactness` value is malformed.

## Completion condition

The product is complete when both tiers are satisfied for the whole indexed source:

**Tier 1 — Coverage** (necessary, not sufficient): every indexed entity is `reconciled`,
`excluded` or `category-record`. The commands are in the Completion condition of
[product-spec.md](product-spec.md).

**Tier 2 — Implementation** (necessary and sufficient with Tier 1):
Every entity selected by a capability record's `sage` selectors passes same-input
oracle comparison against the Sage image pinned in `docs/oracles.md`. The oracle image
is `ghcr.io/dzackgarza/sage@sha256:dadfded3a44fb8314266afb3225855b5ba531b49a53ac70ed844b457435fcfc0`.

Tier 1 completion is tracked by `inventory/coverage.json` (updated by `sage-inventory coverage`).
Tier 2 completion is tracked per-capability in milestone acceptance.

**What does not count as completion**:
- Capability records existing without selectors
- Probes passing `just test` (this is architecture acceptance, not product completion)
- Formal proofs alone (a noncomputable theorem does not discharge an executable requirement)
- Milestone tracking issues being closed (milestones are progress partitions, not the product definition)

## Ownership boundaries

| Component type | Owner | Example |
|---|---|---|
| Mathematical object identity and axioms | `lean-categories` | `cat.rings`, `obj.rings.integers`, `op.rings.add` |
| Language admission, wire types, kernel protocol | `lean-cas-dsl` | `CasCatalogue/Admission.lean`, `Wire`, `StructuredResult.Result` |
| Native computation under catalogue contract | This repository | `LeanSagePort/Euclidean/Gcd.lean` implementing `mor.sets.gcd` |
| Released executable algorithm | `leanprover/hex` | `HexArith.extGcd`, `HexPoly.gcd`, `HexSmith.snf` |
| Formal mathematical proof (noncomputable) | Mathlib | `EuclideanDomain.gcd`, `Matrix.rank`, `HomologicalComplex` |
| Reference oracle | Sage, PARI, GAP, FLINT | Not a runtime computation provider |

**Decision rules**:
1. If a proposed addition is a new mathematical type or axiom → report gap to `lean-categories`
2. If it is a new language feature or stable id → report gap to `lean-cas-dsl`
3. If an existing Hex component covers it → reuse Hex; do not reimplement
4. If Mathlib has the proof (noncomputable) but no Hex executable → write native computation here
5. If neither Mathlib nor Hex has it → write native computation here, optionally write proof

**What belongs here**: The `NativeCompute` adapter for catalogue operations; representation
bridges from Hex data types to catalogue mathematical objects; algorithm implementations for
operations not covered by Hex; acceptance test infrastructure.

**What does not belong here**: New mathematical object definitions; competing stable-id
catalogues; opaque external-engine calls at computation time (Sage/PARI/GAP as runtime providers).
